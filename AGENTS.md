# AGENTS.md — FinnGenUtilsR

FinnGenUtilsR is an **R package** of utility functions for working with FinnGen
data inside the FinnGen Sandbox (a secure analysis environment). It provides:
connection helpers for FinnGen's BigQuery databases (register data and OMOP
CDM), functions that enrich longitudinal/service-sector/Kanta data with
human-readable code/provider/visit info (via `bigrquery` or `dbplyr`), data
summary reports, and a client for the Sandbox GWAS API. Standard R package
layout, no server/API of its own — this package is installed and used inside
notebooks/scripts running in the Sandbox.

## Layout

- `R/` — all source, one theme per file:
  - `fg_connection.R`, `fg_DatabaseConnector.R` — build BigQuery/`DatabaseConnector`
    connections from an `environment` string (`"build"`, `"preview"`,
    `"sandbox-N"`).
  - `fg_bigquery.R` — `fg_bq_tables` R6 class: resolves table paths for a data
    freeze/version and exposes them as `dplyr::tbl` objects.
  - `fg_CDMConnector.R` — OMOP CDM connection via the `CDMConnector` package
    (Suggests-only; guarded by `requireNamespace`).
  - `fg_append_code_info_to_*`, `fg_append_provider_info_*`,
    `fg_append_visit_type_info_*` — each ships **two parallel
    implementations** of the same logic: a `*_sql` / `fg_bq_*` version using
    raw SQL + `bigrquery::bq_project_query()`, and an `fg_dbplyr_*` version
    using lazy `dbplyr` tables. Keep both in sync when changing the join logic.
  - `fg_data_summaries.R` — renders an Rmd/HTML summary report over an
    `fg_bq_tables` object.
  - `connectAndRunGWASAnalysis.R` — HTTP client (`httr`) for the Sandbox GWAS
    API; not a DB function.
- `inst/sql/` — SQL templates for the append_* SQL variant, rendered with
  `SqlRender` (BigQuery dialect directly — no `sql_server`/translate split;
  this package targets BigQuery only).
- `inst/csv/tables.csv` — table-path templates (`table_id`,
  `table_path_template`, `first_data_freeze`) consumed by `fg_bq_tables`.
- `vignettes/` — the real usage docs; check these before assuming how a
  function is meant to be called.
- `tests/testthat/` — real-BigQuery integration tests (see Testing).
- `man/` — generated by roxygen2; don't hand-edit, run `devtools::document()`.

Full rules in **[development/STYLE.md](development/STYLE.md)** — read before writing code.

@development/STYLE.md

Repo-specific notes beyond STYLE.md:

- `fg_` prefix is the existing naming convention for exported functions —
  keep new exports consistent with neighboring functions in the same file
  rather than inventing a new scheme.
- Input validation with `checkmate` (`assertString`, `assert_class`, etc.) at
  the top of exported functions — follow the existing `.assertEnvironment`-style
  pattern.
- This package's SQL is BigQuery-only (unlike a multi-dialect OHDSI package),
  so there's no `sql_server` canonical/translate split to maintain — templates
  in `inst/sql/` are BigQuery SQL directly, still parameterised with `@param`
  placeholders rendered via `SqlRender::render()`.
- When touching an `fg_append_*` feature, update **both** the SQL/`bq_*`
  implementation and its `dbplyr` counterpart — they're intentionally kept
  side by side and tested for equivalent output.

## Development

- `devtools::document()` after changing any exported function or its roxygen
  comments (regenerates `man/` and `NAMESPACE`).
- Everything here talks to **real FinnGen BigQuery projects**
  (`atlas-development-270609` for `environment = "build"`,
  `fg-production-sandbox-*` for other environments) — there is no local/mock
  DB fixture. Most functions and all tests require live GCP access.

## Testing

- `devtools::test()` (testthat edition 3).
- Requires `GCP_SERVICE_KEY` (path to a GCP service account key) in the
  environment — `tests/testthat/setup.R` calls `bigrquery::bq_auth()` with it
  and points tests at the `atlas-development-270609` sandbox project. Without
  it, BigQuery-backed tests will fail to authenticate rather than skip.
- `tests/testthat/helper.R` provides `test_rename()` to suffix temp table
  names with the R version/OS/timestamp — reuse it for any test that creates
  a temp BigQuery table, to avoid collisions between parallel CI runs.
- Tests create and query real (temporary) BigQuery tables — clean up any
  table you create in a new test.

## Building

- Run `devtools::check()` before opening a PR — CI (`R-CMD-check.yaml`) runs it
  on pushes/PRs. Note CI needs `GCP_SERVICE_KEY` as a secret to pass; a fork
  without it will fail the BigQuery-dependent checks.
- `pkgdown.yaml` builds and publishes the docs site
  (https://finngen.github.io/FinnGenUtilsR/) — don't hand-edit `docs/`.

## Git

- **NEVER run `git commit` unless the user's most recent message explicitly
  asks for a commit right now.** Making further edits, fixing a bug, or
  finishing a task the user asked for is NOT permission to commit it — leave
  the changes uncommitted in the working tree and say what's ready to commit.
  An earlier "commit" instruction covers only the changes that existed at
  that moment, never work done afterward. If in doubt, ask instead of
  committing.
- Feature branch → PR into `development`. Don't push directly to
  `development`/`main`; only a human opens the `development` → `main` release PR.
- When asked to commit, use the `commit` skill (`.claude/skills/commit/`) for
  Conventional Commits formatting and safety checks.
- Use the `pull-request` skill (`.claude/skills/pull-request/`) to open PRs —
  it runs `devtools::check()` and targets `development`.
- Bump `Version` in `DESCRIPTION` and add a `NEWS.md` entry for user-visible
  changes, following the existing terse bullet style.

## Security

- `GCP_SERVICE_KEY` is a service-account credential — never read, print, log,
  or commit its value or the key file it points to.
- Don't touch BigQuery auth/connection code
  (`fg_connection.R`, `fg_DatabaseConnector.R`, `bigrquery::bq_auth` calls) or
  the Sandbox API token handling in `connectAndRunGWASAnalysis.R` without a
  human explicitly asking.
